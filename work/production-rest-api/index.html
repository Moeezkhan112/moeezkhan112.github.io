01 / The challenge

Start with the problem.

A basic CRUD API is easy to start but becomes difficult to operate when persistence, caching, background work, observability and infrastructure concerns are mixed into the same application flow.

Business requirement

Design a backend foundation that can support SaaS platforms, CRM integrations, internal business APIs and data-intensive workloads while allowing infrastructure components to evolve independently from request-handling code.

02 / The approach

Connect the moving parts.

  1. 01

    Built the API layer with Node.js, Express and TypeScript, keeping routes, middleware and service logic separated.

  2. 02

    Used PostgreSQL with Prisma for structured persistence and Redis for high-performance cached access.

  3. 03

    Moved asynchronous work into BullMQ queues and background workers instead of blocking API requests.

  4. 04

    Added OpenTelemetry as the observability layer and Docker-based infrastructure for a repeatable runtime environment.

03 / Engineering decisions

The thinking behind the work.

Separate application and infrastructure concerns

Routes, services, middleware, queues and infrastructure are kept distinct so a change in one area does not force the entire backend to be redesigned.

Use the right data path for the workload

PostgreSQL remains the structured source of truth while Redis handles cacheable reads and BullMQ handles work that should not extend request latency.

Make observability part of the architecture

OpenTelemetry is included as a first-class layer so tracing and operational visibility are considered before production incidents happen.

05 / Production thinking

Reliability before scale.

Reliability
  • Keep long-running tasks outside the request path
  • Centralize error handling and configuration
  • Use caching for repeat-access paths
  • Trace request and service behaviour with OpenTelemetry
Security & boundaries
  • Keep environment-specific configuration outside application code
  • Validate request boundaries before business logic
  • Keep data-access and queue concerns behind service interfaces
